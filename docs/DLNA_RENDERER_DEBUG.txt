What is broken
--------------
1. ffmpeg cannot pull HTTPS
   ffmpeg -i https://example.com/ → “Protocol not found”.
   HostPlayer.play_url() accepts https://, then ffmpeg fails with
   stderr on DEVNULL, so Settings often shows a generic play failed
   or nothing. iPhone / some Android DLNA apps hand the renderer an
   https URL. HTTP from BubbleUPnP’s local server should still work.

2. GetCurrentTransportActions is empty
   Not in AVTransport.xml. SOAP returns HTTP 200 with an empty
   GetCurrentTransportActionsResponse (no CurrentTransportActions).
   BubbleUPnP, VLC, and Windows “Cast to Device” use this to decide
   whether Play/Pause/Seek are allowed. Empty → controls stay dead
   even though the device is listed.

3. Failed Play is not a UPnP fault
   Play with no CurrentURI → HTTP 500 and an empty <u:PlayResponse>.
   Spec wants a SOAP Fault (UPnPError 701/402). Controllers that
   parse faults vs 500 + empty response mis-handle the error.

4. HTTP Server header is Python, not UPnP
   device.xml / SOAP replies send:
     Server: BaseHTTP/0.6 Python/3.8.17
   SSDP uses a correct SERVER line. Some stacks drop devices whose
   description HTTP Server header is not “OS/ver UPnP/1.0 Product/ver”.

5. Play errors are silent
   ffmpeg|paplay stderr is DEVNULL. A bad URI, HTTP 404 from the
   phone, or the HTTPS protocol miss never reaches dlna.error.

6. Smaller spec gaps (less likely to hide the device, more likely
   to break a specific app)
   - No GetCurrentTransportActions / SetNextAVTransportURI in SCPD
   - Volume has no allowedValueRange 0–100
   - No iconList
   - modelNumber still 0.7
   - SSDP replies omit BOOTID.UPNP.ORG (Sonos/HEOS on this LAN send it)
   - SOAP 500 path does not emit <s:Fault>

- Firewall
- SSDP multicast join (maddr shows 239.255.255.250 on eth0)

Likely user-visible story
-------------------------
Phone finds “Gigawatt”. Tap Play does nothing or errors:
  - app asked GetCurrentTransportActions, got empty
  - or SetAVTransportURI + Play with https://, ffmpeg cannot open it
  - or Play 500 with no SOAP fault

HTTP from BubbleUPnP to a LAN file should still be able to play if
the controller ignores the empty transport-actions response.
